# 设计：add-ai-context-memory

## 关键决策

### D1：客户端驱动压缩 + 服务端摘要合并（而非服务端全权管理）

前端持有全部历史并计算窗口；超窗时把「尚未被摘要覆盖、且将被移出窗口」的消息发给后端。后端做纯摘要合并（已有摘要 + 新增对话 → 一份新摘要），不存任何会话状态。理由：与现有架构一致（后端无会话存储），避免每请求重复摘要的浪费，刷新恢复后逻辑不变。

### D2：按轮截断 = 从切断点向后找最近 user 消息

`cut = list.length - max`，向后推进到第一条 user 消息。被跳过的轮次碎片不进窗口、进入摘要载荷（对模型而言比协议 400 更好）。窗口尾部天然完整（取的是尾部）。不变量：`list[covered]` 永远是一条 user 消息或 `== list.length`。

### D3：摘要以 role=system 消息注入（非 user）

后端 `toDeepMessages` 已支持 system 角色；摘要属元上下文，用 system 语义最准确，也避免模型把它当作用户发言。前端 `AiWireMessage.role` 联合类型扩展 `'system'`。该消息仅存在于发送时的 wire 构造中，不进 UI 列表、不会被 history 事件回显。

### D4：摘要失败降级不阻断

摘要接口失败（余额/网络/超时）时：接受截断（covered 推进），对话照常继续。宁可丢旧细节也不让当前提问失败。摘要进行中并发发送的场景：跳过本轮摘要，covered 不推进，下轮重试（dropped 会重新计算，不会丢）。

### D5：持久化按用户隔离 + 写入时机收敛

localStorage key `vben-ai-chat-v1:{userId}`；持久化在轮次结束（finishRound）、清空、确认卡片终态时触发，而非 deep-watch 每个流式 delta（避免每 token 一次 JSON.stringify）。存储上限 500 条，裁剪头部时同步平移 covered。messageIdSeed 从恢复数据的 max(id)+1 续号。

### D6：摘要提示词约束

中文、≤300 字、只保留对象/目标/已执行操作与结果/关键参数/未完成事项、禁止编造；tool 结果截断 120 字、消息截断 500 字、最多 80 条，控制摘要调用成本。

## 风险与取舍

- 摘要调用增加 2~5s 延迟：仅超窗时发生，可接受
- 恢复的确认卡片仍可确认执行：toolCallId 服务端本就不校验，幂等安全
- 不同标签页同时写入：后写覆盖先写，单用户场景可接受
