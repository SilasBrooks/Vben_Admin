# ai/assistant Specification

## Purpose

在管理后台提供右下角自然语言智能助手：流式对话查询用户/角色/部门，新增类写操作经用户显式确认并经服务端权限校验后执行，降低系统操作门槛。

## Requirements

### Requirement: 悬浮入口与会话面板

系统 MUST 在用户登录后的主框架所有页面右下角提供固定的圆形 AI 助手入口按钮，图标使用 `public/logo.png`；登录/认证页面 MUST NOT 显示该入口。点击按钮 MUST 从右侧滑出聊天面板，再次点击关闭按钮 MUST 收起面板。

面板 MUST 支持：流式消息展示、文本输入（Enter 发送、Shift+Enter 换行）、生成过程中停止、清空当前会话、空状态下展示推荐问题。会话历史第一版仅保存在浏览器内存，刷新页面后清空是可接受行为。

#### Scenario: 登录后看到入口

- **WHEN** 用户登录后进入任意主框架页面
- **THEN** 右下角显示圆形 logo 助手按钮，点击后滑出聊天面板

#### Scenario: 登录页不显示入口

- **WHEN** 未登录用户访问登录页
- **THEN** 页面不出现 AI 助手按钮与面板

### Requirement: 流式对话协议

前端 MUST 通过 `POST /api/ai/chat` 与后端通信，后端 MUST 以 SSE（Server-Sent Events）返回，事件类型 MUST 为固定四种：`delta`（文本片段）、`toolcall`（需要确认的写操作）、`done`（本轮结束）、`error`（错误提示）。模型接口凭据（API Key、接口地址、模型名）MUST 仅保存在后端，任何接口响应 MUST NOT 包含 Key 明文。

后端 MUST 按以下顺序解析每次对话使用的底层大模型（OpenAI 兼容协议）：

1. `sys_llm_config` 中 `is_active=1 AND enabled=1` 的唯一激活配置；
2. 未命中激活配置时，回退 yml `deepseek.*` 兜底配置。

解析 MUST 在每次对话开始时执行一次并在整次对话（含多轮工具调用）内固定；配置新增、编辑或激活后 MUST 无需重启即时生效。激活配置不可用（连接失败/认证失败）时 MUST 返回可读中文错误，MUST NOT 静默切换到兜底配置或其他配置。

前端 MUST 使用 fetch + ReadableStream 读取流，并在发起新请求或清空会话时中断上一条未完成的流，避免多条流并发写同一会话。

#### Scenario: 普通问答流式输出

- **WHEN** 用户发送与系统操作无关的问题
- **THEN** 回复文字以打字机方式逐段出现在助手气泡中，结束后收到 done 事件

#### Scenario: 对话使用激活配置

- **WHEN** 管理员在模型配置页将激活配置从 A 切换为 B
- **THEN** 此后的 AI 对话 MUST 使用 B 配置的接口地址、Key 与模型发起请求，全程无需重启服务

#### Scenario: AI 服务未配置

- **WHEN** 后端既无激活模型配置、yml 兜底也未配置 API Key
- **THEN** 前端收到 error 事件并在气泡中显示"AI 服务未配置"类提示（引导至系统管理-模型配置），不抛出未捕获异常

#### Scenario: 激活配置不可用不静默降级

- **WHEN** 激活配置的接口地址无法连接
- **THEN** 前端收到 error 事件并显示「AI 服务暂时不可用」类可读错误，系统 MUST NOT 静默改用兜底配置应答

### Requirement: 工具集与两档执行语义

系统 MUST 内置覆盖系统管理、监控、内容、消息聊天等模块的 AI 工具集，全部以 `@AiAgentTool` 注解声明在 `module/ai/tool/` 下的 `@Component` 类中，启动时反射扫描自动注册，新增工具 MUST NOT 修改注册表或分发代码。工具按功能域分组：

- 系统管理查询/写入：用户、角色、部门、菜单、字典、文件的查询与用户/角色/部门/公告创建，用户/角色/部门删除，密码重置，角色菜单授权（高危）
- 监控查询：在线用户、登录日志、操作日志、仪表盘统计
- IM 消息聊天：联系人、会话、历史查询与消息发送（见「IM 消息聊天工具」需求）

- **查询类工具**：当模型发起调用时，后端 MUST 在同一次请求内自动执行、把结果回喂模型继续作答，MUST NOT 要求用户确认。
- **写操作类工具**：后端 MUST NOT 直接执行，MUST 通过 toolcall 事件把结构化参数下发给前端展示确认卡片；仅当用户显式确认后，经 `POST /api/ai/tool/execute` 才可落库。高危工具在多步计划中另需二次确认。

工具参数 MUST 支持以中文名称或登录名指代引用对象（如部门名、角色名、用户名），由后端解析为实际 id；无法解析时 MUST 返回可读错误让模型追问，MUST NOT 猜测或自动创建引用对象。

#### Scenario: 查询自动执行

- **WHEN** 用户问"系统里有哪些部门"
- **THEN** 后端自动执行部门查询并由模型基于真实数据流式回答，全程不出现确认卡片

#### Scenario: 新增必须确认

- **WHEN** 用户说"帮我新增一个角色叫财务专员"
- **THEN** 对话框出现包含角色名等参数的确认卡片，且在用户点击确认前数据库中 MUST NOT 出现该角色

#### Scenario: 确认后执行并反馈

- **WHEN** 用户在确认卡片上点击"确认执行"
- **THEN** 后端完成落库，卡片显示执行结果，随后模型用中文汇报创建结果（含新对象标识）

#### Scenario: 取消新增

- **WHEN** 用户在确认卡片上点击"取消"
- **THEN** 不发生任何数据变更，卡片标记为已取消，助手确认操作已取消

### Requirement: 菜单树查询工具

系统 MUST 提供 `query_menus` 查询类工具（权限码 `System:Menu:List`）：返回菜单全集的精简字段（id、菜单名、类型 M/C/F、上级 id、权限码、状态），供模型了解可分配范围。查询类工具按既有语义自动执行，MUST NOT 要求用户确认。

#### Scenario: 查询菜单树自动执行

- **WHEN** 用户问"系统里有哪些菜单"
- **THEN** 后端自动执行菜单查询并由模型基于真实菜单数据作答，全程不出现确认卡片

### Requirement: 角色菜单授权工具

系统 MUST 提供 `assign_role_menus` 写操作工具（权限码 `System:Role:Auth`）：参数为角色（中文名或 roleKey）与菜单中文名数组。后端 MUST 将名称解析为 id 并按以下规则补全：

- 目录名 → 该目录及全部后代（含按钮）
- 菜单名 → 该菜单 + 全部祖先目录 + 其直属按钮
- 按钮名 → 该按钮 + 全部祖先目录链

名称匹配到 0 个或多个时 MUST 返回可读错误让模型追问，MUST NOT 猜测。该工具属新增类写操作语义：MUST 经 toolcall 确认卡片、用户显式确认后执行；执行采用全量替换语义重建该角色菜单授权，执行结果 summary MUST 明示"全量替换"与生效菜单数量。

#### Scenario: 按目录名整模块授权

- **WHEN** 用户确认"给库存管理员分配库存管理"
- **THEN** 库存管理目录及其全部子菜单与按钮被授权给该角色，卡片显示菜单数量

#### Scenario: 授权自动补全父级

- **WHEN** 用户确认"给财务专员分配用户管理"
- **THEN** 系统管理目录（祖先链）、用户管理菜单及其按钮权限码一并写入角色菜单，该角色用户登录后可完整看到并使用该页面

#### Scenario: 名称歧义追问

- **WHEN** menuNames 中某名称匹配到 0 个或多个菜单
- **THEN** 不执行授权，返回可读错误由模型向用户追问，数据库无变更

#### Scenario: 全量替换语义告知

- **WHEN** 角色已有菜单授权且用户确认新的分配
- **THEN** 旧授权被整体替换，summary 明示"全量替换"与菜单数量

### Requirement: 服务端权限校验

每一个工具 MUST 映射到既有的功能权限码（查询→对应模块 `:List`，新增→对应模块 `:Add`/`:Auth`）。后端在执行工具前 MUST 基于当前登录用户重新校验权限码；前端入口与确认按钮不作为安全边界。权限不足时 MUST 返回可由模型转述的中文错误，MUST NOT 执行该操作。

编排循环中，写操作工具的 toolcall 确认事件 MUST NOT 下发给无对应用户权限的请求：模型调用无权限的写操作工具时，系统 MUST 将权限不足结果回喂模型继续本轮对话，由模型直接告知用户"你的权限不足"；确认卡片仅在用户具备对应权限时出现。确认执行接口 `POST /api/ai/tool/execute` MUST 保留独立权限校验作为纵深防御。

#### Scenario: 无新增权限的用户指令被拒绝

- **WHEN** 没有 System:Dept:Add 权限的登录用户要求 AI 新增部门
- **THEN** 确认后执行返回无权限错误，数据库无变更，助手回复解释缺少权限

#### Scenario: 无权限用户请求写操作直接获知权限不足

- **WHEN** 没有 System:User:Add 权限的登录用户要求 AI 创建用户
- **THEN** 助手直接回复"你的权限不足"并说明缺少的权限，全程不出现确认卡片，数据库无变更

#### Scenario: 无权限用户请求查询获知权限不足

- **WHEN** 没有 System:User:List 权限的登录用户询问"系统里有哪些用户"
- **THEN** 查询工具自动执行失败并回喂模型，助手回复"你的权限不足"，不出现编造数据

### Requirement: 上下文记忆与持久化

系统 MUST 对会话上下文实施窗口管理：窗口按完整对话轮次（以 user 消息为轮次起点）截断，MUST NOT 产生孤立的 tool 或 assistant(tool_calls) 消息导致上游协议错误。窗口默认保留最近 50 条协议消息。

被移出窗口的历史轮次 MUST 经服务端摘要接口（`POST /api/ai/chat/summarize`，由当前激活的大模型生成）与已有摘要合并为一份「此前对话摘要」，以 system 消息随每次对话请求注入。摘要过程 MUST 对用户透明；摘要失败时 MUST 降级为直接截断并保证当前对话继续，MUST NOT 阻断提问。

会话（消息、摘要、覆盖进度、确认卡片状态）MUST 按用户隔离持久化于浏览器本地存储，刷新页面后恢复；用户清空会话时 MUST 同步清除本地存储。服务端 MUST NOT 存储会话状态。

#### Scenario: 超窗按轮截断保证协议配对

- **WHEN** 历史消息数超过窗口上限且切断点落在一轮工具对话的中间
- **THEN** 窗口起点向后推进到最近一条 user 消息，被跳过的碎片仅进入摘要载荷，上游不返回协议错误

#### Scenario: 旧轮次滚动摘要注入

- **WHEN** 有历史轮次被移出窗口
- **THEN** 系统将其与已有摘要合并生成新摘要，并作为 system 消息随后续每次请求注入，用户无感知

#### Scenario: 摘要失败降级

- **WHEN** 摘要接口调用失败（余额不足/网络异常等）
- **THEN** 当前提问照常发送与回答，旧轮次被直接截断，不出现报错气泡

#### Scenario: 刷新页面后会话恢复

- **WHEN** 同一用户刷新页面后重新打开助手
- **THEN** 历史消息、摘要与确认卡片状态恢复，可继续此前话题；不同用户的本地会话互不可见

#### Scenario: 清空会话清除本地存储

- **WHEN** 用户点击清空会话
- **THEN** 界面消息与本地存储同时清空，下次打开为全新会话

### Requirement: 数据安全与结果裁剪

回喂给模型的查询结果 MUST 经过字段裁剪，MUST NOT 包含用户密码等敏感字段。写操作结果 MUST 经过现有 Admin Service 落库（复用既有校验与填充逻辑），MUST NOT 绕过业务层直接写表。单条用户消息超过 1000 字时 MUST 截断；会话历史超窗时按「上下文记忆与持久化」需求的规则截断（服务端保留 60 条兜底防线）。

#### Scenario: 查询用户结果不含敏感字段

- **WHEN** AI 调用查询用户工具并返回用户列表给模型
- **THEN** 结果中每个用户只包含 id、用户名、昵称、部门名、角色名、状态等必要字段，MUST NOT 包含密码、密码盐或 token 类字段

#### Scenario: 超长输入被截断

- **WHEN** 用户发送超过 1000 字的消息或会话历史超过 20 条
- **THEN** 系统截断后再发送给模型，接口正常返回，不出现因超长导致的服务端异常

### Requirement: IM 消息聊天工具

系统 MUST 提供 4 个 IM 消息聊天工具，全部为登录即可调用（无权限码，与 IM REST 接口语义一致）：

- `query_im_contacts` 查询类：返回全部启用状态的其他用户（username、nickname），供模型确定消息接收人。
- `query_my_conversations` 查询类：返回当前用户会话列表（对方 username/nickname、最后一条消息、未读数），最近活跃在前。
- `query_chat_history` 查询类：参数 username（对方登录名）与可选 limit（默认 20，上限 50），返回与该对方的聊天记录（时间正序，含发送方向、内容、是否已读、时间）。
- `send_chat_message` 写操作类：参数 username 与 content（≤500 字），MUST 经 toolcall 确认卡片、用户显式确认后经 `ImChatService.send` 落库并实时推送；执行结果 summary MUST 包含接收人与消息内容概要。

username 解析 MUST 精确匹配唯一用户；0 个或多个匹配 MUST 返回可读错误让模型追问。发送工具 MUST 复用既有校验：接收人不存在或停用即失败、MUST NOT 允许给自己发消息。查询结果 MUST 仅覆盖本人参与的消息（单侧删除的消息按既有语义过滤）。

#### Scenario: 查询联系人自动执行

- **WHEN** 用户问"我能给谁发消息"
- **THEN** 后端自动执行联系人查询并由模型基于真实数据作答，全程不出现确认卡片

#### Scenario: 发消息必须确认

- **WHEN** 用户说"给 jack 发条消息说明天开会"
- **THEN** 对话框出现包含接收人 jack 与消息内容的确认卡片，用户确认前数据库中 MUST NOT 出现该消息

#### Scenario: 确认后发送成功

- **WHEN** 用户在确认卡片上点击"确认执行"
- **THEN** 消息落库且对方在线时实时送达，summary 明示「已发送给 jack」，模型据此汇报

#### Scenario: 用户名不存在追问

- **WHEN** send_chat_message 或 query_chat_history 的 username 匹配不到用户
- **THEN** 不执行任何操作，返回可读错误由模型向用户追问确认接收人

### Requirement: Markdown 渲染与 XSS 防护

助手消息内容 MUST 以 Markdown 渲染展示，至少支持：标题、有序/无序列表、表格、行内代码、代码块（带语法高亮）、链接、引用、粗体/斜体。用户气泡 MUST 保持纯文本渲染，MUST NOT 对用户输入应用 HTML 渲染。

模型输出不可信：Markdown 渲染 MUST 遵循双重防线——解析器 MUST 禁用原始 HTML 透传（模型输出中的 HTML 标签按转义文本展示），渲染产物 MUST 经 DOMPurify 消毒后方可通过 `v-html` 注入 DOM。

流式输出期间 MUST 采用节流重渲策略（整体重渲 + 定时刷新），MUST NOT 对每个 delta 片段单独执行完整解析；本轮流结束（done/stop/error）时 MUST 以完整文本执行一次最终渲染。流式过程中出现未闭合的代码围栏 MUST 容忍（按容错规则渲染），MUST NOT 报错或中断渲染，文本完整后渲染结果自动纠正。

确认卡片与计划卡片的展示、交互 MUST NOT 受 Markdown 渲染影响；错误提示气泡 MUST 保持纯文本样式。

#### Scenario: Markdown 正常渲染

- **WHEN** 模型回复包含标题、列表、表格与行内代码
- **THEN** 气泡内按 Markdown 样式渲染（层级标题、列表符号、表格线框、行内代码底色），不出现原始 Markdown 符号

#### Scenario: 代码块语法高亮

- **WHEN** 模型回复包含带语言标注的代码块（如 ```sql）
- **THEN** 代码块以高亮配色渲染，与对话主题风格协调

#### Scenario: 恶意输出被消毒

- **WHEN** 诱导模型回复中包含 `<script>alert(1)</script>` 或 `<img onerror>` 等内容
- **THEN** 页面不执行任何脚本、不弹窗，相关内容以转义文本或被剥离后的安全节点展示

#### Scenario: 流式未闭合围栏容忍

- **WHEN** 流式输出过程中代码围栏尚未闭合
- **THEN** 渲染持续进行不报错（围栏后内容按代码块容错渲染），围栏闭合后渲染自动纠正

#### Scenario: 确认卡与计划卡不受影响

- **WHEN** 助手消息同时包含 Markdown 正文与确认卡片/计划卡
- **THEN** 正文按 Markdown 渲染，卡片标题、参数表格与按钮行为与既有交互完全一致

#### Scenario: 用户气泡保持纯文本

- **WHEN** 用户输入包含 `<b>bold</b>`、`*斜体*` 等 Markdown/HTML 语法
- **THEN** 用户气泡按输入原文展示，不做任何 HTML 渲染

### Requirement: 代码块复制与长代码折叠

助手消息中的代码块 MUST 在块头部展示语言标识（围栏标注的语言；未标注语言时展示 `text` 或留空），并提供复制按钮，点击后将代码块完整内容写入系统剪贴板并给出短暂成功反馈。复制 MUST NOT 包含语言标签与按钮自身文本。

超过 20 行的代码块 MUST 默认折叠（限制展示高度并给出可感知的展开入口），用户 MUST 能展开完整内容并再次收起。折叠状态 MUST NOT 影响复制功能（折叠态复制的是完整代码）。

代码块结构 MUST 经既有 XSS 防线（解析器禁用原始 HTML + DOMPurify 消毒）后注入，注入的按钮与标签 MUST NOT 引入脚本执行风险。

#### Scenario: 语言标签与复制

- **WHEN** 模型回复包含 ```sql 代码块，用户点击复制按钮
- **THEN** 块头部显示 `sql` 语言标识，完整 SQL 文本进入剪贴板，按钮短暂显示复制成功态

#### Scenario: 长代码默认折叠

- **WHEN** 模型回复包含 25 行的代码块
- **THEN** 代码块默认折叠为受限高度（含展开入口），点击展开后完整可见，可再次收起；折叠态下点击复制仍得到完整 25 行内容

#### Scenario: 短代码不折叠

- **WHEN** 模型回复包含 8 行的代码块
- **THEN** 代码块完整展示，不出现折叠入口

#### Scenario: 注入结构不逃逸

- **WHEN** 代码内容本身包含 `<button>`、`<script>` 等文本
- **THEN** 代码内容按转义文本展示，页面不出现可交互的多余按钮、不执行脚本

### Requirement: 消息区自动滚动跟随

流式输出与消息更新引发的列表增长，MUST 仅在用户视口位于消息区底部附近（阈值内）时自动滚动到底；用户向上翻阅历史时 MUST NOT 被强制拉回底部，用户滚回底部附近后自动恢复跟随。用户主动发送消息、点击建议项产生的新对话轮次 MUST 滚动到底部展示。

#### Scenario: 流式中上翻不被拉回

- **WHEN** 模型正在流式输出，用户向上滚动消息区阅读历史
- **THEN** 输出继续但视口保持用户所在位置，不自动跳回底部

#### Scenario: 滚回底部恢复跟随

- **WHEN** 用户在流式输出中向上翻阅后，将消息区滚回底部附近
- **THEN** 后续输出重新自动滚动跟随

#### Scenario: 新发消息定位底部

- **WHEN** 用户发送一条新消息或点击建议项
- **THEN** 消息区滚动到底部，新消息与随后出现的回复气泡可见
